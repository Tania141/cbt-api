# Ако не работи

*Какво да гледам, когато нещо спре да отговаря. Подредено по симптом — този,
който се вижда от PWA, не този, който се вижда в кода.*

---

## Симптом: цялото API не отговаря след деплой

PWA казва „API не е конфигуриран“ или всяка заявка увисва / дава грешка.

**Първо място за гледане: логовете на Railway, най-горе, при старта.**

Причината почти винаги е една: **API-то не е тръгнало изобщо.** Не че е тръгнало
и после се е счупило — не е стартирало.

### Защо се случва

При пускане Railway изпълнява `gunicorn api:app`. За да получи `app`, gunicorn
трябва да прочете целия `api.py` — а на последния ред на файла стои:

```python
init_db()
```

Тоест **свързването с базата се случва при стартиране, преди първата заявка.**
Ако `DATABASE_URL` е зададен, но базата е недостъпна в този момент, връзката
хвърля грешка, четенето на файла спира дотам, `app` така и не се получава и
gunicorn се предава.

Резултатът за теб изглежда като „API-то е счупено", а всъщност базата е била
недостъпна за няколко секунди при пускането.

### Какво да направя

1. Виж логовете на Railway при старта. Търси думи като `could not connect`,
   `connection refused`, `psycopg2`.
2. Провери дали PostgreSQL услугата в Railway работи и дали `DATABASE_URL` е
   закачен към API услугата.
3. Пусни деплой наново. Ако базата е била в рестарт, вторият опит минава.

### Как да разбера, че е точно това

Ако `DATABASE_URL` изобщо липсва, API-то **тръгва** нормално и в логовете пише
`DATABASE_URL не е зададен — PostgreSQL пропуснат`. Тогава всички неща, които
искат база (паспорти, заповедни книги, потребители), връщат
`База данни не е конфигурирана`, но самото API отговаря.

Тоест:

| В логовете | Значи |
|---|---|
| нищо, gunicorn не е тръгнал | базата е била недостъпна при старта |
| `DATABASE_URL не е зададен` | променливата липсва, API-то работи без база |
| API отговаря, но `503` по заявките | същото — липсва база |

## Симптом: нова таблица „я няма“ след деплой

Например „Заповедни книги“ дава грешка веднага след като е добавен регистърът.

**Не се прави нищо ръчно.** Таблиците се създават сами при всяко стартиране на
API-то — в `init_db()` стоят редове от вида:

```sql
CREATE TABLE IF NOT EXISTS zapovedni_knigi (...)
ALTER TABLE tenants ADD COLUMN IF NOT EXISTS zk_nachalen_nomer INTEGER
```

`IF NOT EXISTS` значи „ако вече я има — не пипай“. Затова:

- нищо не се пресъздава и **никакви данни не се губят** при рестарт;
- може да се рестартира колкото пъти трябва;
- няма отделна стъпка „миграция“ — схемата се догонва сама.

Ако таблицата липсва, значи `init_db()` не е стигнал дотам — тоест сме в
първия симптом по-горе: API-то не е тръгнало. Гледай логовете при старта.

**Важно:** таблицата се създава при **старта**, не при първото отваряне на
изгледа. Отварянето на „Заповедни книги“ само чете — то не създава нищо.

## Симптом: документ излиза с `{{Нещо}}` в текста

Маркер в шаблона, за който няма ключ в кода. Пусни от корена на `cbt-api`:

```
python tools/check_templates.py
```

Той хваща това преди клиента. Подробностите са в
`templates/КОНВЕНЦИЯ.md`.

---

## Симптом: поле в документа излиза празно

Кодът чете ключ, който PWA не праща (или обратно). Пусни:

```
python tools/check_keys.py
```

Разминат етикет **не гърми**: кодът не намира ключа, слага празно и
продължава. Документът изглежда наред, но на едно място не пише нищо.
